The `subscription` plugin keeps billing state next to identity. It hands the money side to
the [Ledger](/docs/bridges/ledger) engine and spends its own effort on the parts that touch
auth: who the tenant is, who in an organization may change the plan, and whether a tenant is
entitled to a feature.

## Setup

```go
import (
    "github.com/xraph/authsome"
    "github.com/xraph/authsome/plugins/subscription"
)

eng, err := authsome.NewEngine(
    // plus WithStore, WithChronicle and WithWarden (see Getting Started)
    authsome.WithLedgerEngine(ledgerEngine),
    authsome.WithPlugin(subscription.New(subscription.Config{
        DefaultPlanSlug:    "free",
        AutoSubscribeOnOrg: true,
    })),
)
```

You need a ledger. Without one the plugin has nothing to delegate to.

## Organizations or users

One app-wide setting, `subscription.tenant_mode`, decides who a subscription belongs to.
In `organization` mode (the default) the tenant is an organization and everyone in it
shares the plan. In `user` mode each user is their own tenant.

Nothing else in the API changes between the two, and you never pass the tenant from your
UI: the plugin takes the session's active organization (or the user, in user mode) and
checks that the caller belongs to it before answering.

<Callout type="info">
In organization mode the session needs an active organization. Switch to one with
`POST /v1/me/switch-org`, or the self-service routes answer 400.
</Callout>

## Self-service

These are the routes a billing page calls, all under `/v1/billing`.

| Method | Path | What it does |
|--------|------|--------------|
| `GET` | `/plans?app_id=...` | Plans you can buy, cheapest first, with their features |
| `GET` | `/subscription` | Your subscription with its plan embedded, or `null`, and `can_manage` |
| `POST` | `/subscription` | Subscribe: `{"plan": "team", "seats": 5}` |
| `PATCH` | `/subscription` | Change plan, seats, or both |
| `POST` | `/subscription/cancel` | Cancel at the period end, or `{"when": "now"}` |
| `POST` | `/subscription/resume` | Take back a scheduled cancellation |
| `GET` | `/entitlements` | Every feature on your plan, checked in one call |
| `POST` | `/portal` | A billing portal link, when your checkout provider has one |

`plan` takes a slug or an ID. Every write answers with the updated subscription, so your
UI can render the response as it is. `/plans` is the one route that wants your `app_id`;
the client config your SDK already fetches carries it.

A few things in that payload are there so the page can say the right thing:

- `can_manage` is false for anyone who'd get a 403 on a write. Hide the buttons for them.
- After a cancellation at the period end, `status` stays `active` and `cancel_at` holds the
  date it ends. Show that date, and offer `/subscription/resume`.
- A `past_due` or `paused` subscription is still the tenant's subscription. `GET` returns it
  and a second subscribe answers 409, so show "update your payment" rather than the pricing
  table. A paused plan can't be changed until an operator resumes it.
- `seats` appears on plans with a seat feature. `used` counts the organization's members
  and `limit` is the number bought, or the plan's limit if none was. A `null` limit means
  unlimited, and so does a `null` feature `limit` on a plan.
- `amount_minor` is the price in cents (or your currency's minor unit). Format it with the
  user's locale; `base_amount` is the same price as a plain string.
- Times are RFC 3339 in UTC.

## Who can change the plan

Reading is open to everyone in the organization. Writing needs two things:

1. `subscription.self_service_upgrade` is on for the app. It is by default.
2. The caller's organization role is listed in `subscription.billing_roles`. Out of the box
   that's `["owner"]`.

`billing_roles` can be set per app and per organization. An organization that wants its
admins to handle billing sets `["owner", "admin"]` for itself, and nobody else is affected.

This lives in settings rather than in an app role because app roles in Warden aren't scoped
to an organization yet (see [Org-Scoped Roles](/docs/organizations/org-scoped-roles)). A
"billing" app role would reach every organization the user belongs to.

Operators holding `billing:manage` pass both checks, and can name any tenant with
`tenant_id`.

## Taking payment

With no checkout provider, subscribing grants the plan straight away, which suits free plans
and trials. To charge, implement `CheckoutProvider`. Once it's set, every subscribe and every
plan or seat change asks it first, and it decides:

```go
type stripeCheckout struct{ client *stripe.Client }

func (s stripeCheckout) Checkout(ctx context.Context, req subscription.CheckoutRequest) (subscription.CheckoutResult, error) {
    if nothingToPay(req) { // a free plan, a downgrade, fewer seats
        return subscription.CheckoutResult{}, nil // applied straight away
    }
    // Create a checkout session for req.Plan, req.Quantity and req.TenantID,
    // send the customer back to req.ReturnURL, and return its URL.
    return subscription.CheckoutResult{URL: session.URL}, nil
}

subscription.New(subscription.Config{Checkout: stripeCheckout{client}})
```

`req.Current` and `req.CurrentPlan` tell you what the tenant has now, so you can tell an
upgrade from a downgrade. When you return a URL the API answers `{"checkout_url": "..."}` and
changes nothing; your client sends the customer there. When your provider's webhook confirms
the payment, finish the change:

```go
sub, err := plugin.CompleteCheckout(ctx, req)
```

Keep whatever you need to rebuild `req` (tenant, app, plan, seats) in the checkout session's
metadata. `CompleteCheckout` is safe to call twice for the same payment, moves whatever
subscription the tenant has by then, and records the same audit entry and event as the API.

Cancelling and resuming never go through the provider. To keep it in step, listen for the
`subscription.canceled`, `subscription.plan_changed` and `subscription.resumed` events and
update or stop the subscription on your provider's side, or a customer who cancels in your
app keeps being charged.

Add a `Portal` method (the `PortalProvider` interface) and `POST /v1/billing/portal`
returns a link to your provider's hosted page for cards and invoices.

If the provider fails, the error goes to your logs and the client gets a 502. Your
provider's error text never reaches the browser.

<Callout type="warn">
Two subscribes for the same tenant at the same moment are serialized inside one process, but
not across replicas: ledger has no per-tenant uniqueness yet. If you run several replicas,
route a tenant's billing writes to one of them, or check for an existing subscription in your
webhook.
</Callout>

## In React

The client half ships as `@authsome/plugin-subscription`. Add it to your provider the way you added the server plugin to the engine:

```tsx
import { subscription } from "@authsome/plugin-subscription";
import { useSubscription, Entitled } from "@authsome/plugin-subscription/react";
import { PricingTable, CurrentPlanCard } from "@authsome/plugin-subscription/components";

<AuthProvider baseURL={url} publishableKey={pk} plugins={[subscription()]}>
  <App />
</AuthProvider>

function Billing() {
  const { plan, subscription, changePlan, isPending } = useSubscription();
  return (
    <>
      <CurrentPlanCard />
      <PricingTable highlight="team" returnUrl={location.href} />
    </>
  );
}

<Entitled feature="sso" fallback={<UpgradePrompt />}>
  <SsoSettings />
</Entitled>
```

Everything reading the subscription shares one cache. A write updates it, a sign-out clears it, and switching organization reloads it. `<Entitled>` shows the fallback until it has a positive answer, so loading or an outage never opens a paid feature.

## In Flutter

Two packages: `authsome_subscription` (pure Dart: models and state) and `authsome_subscription_flutter` (widgets).

```dart
AuthProvider(
  config: AuthConfig(baseUrl: url, plugins: const [SubscriptionPlugin()]),
  child: const MyApp(),
);

const CurrentPlanCard();
PricingTable(onCheckout: (uri) => launchUrl(uri));
const EntitlementGate(feature: 'sso', fallback: UpgradePrompt(), child: SsoSettings());

final billing = context.subscription;
final result = await billing.changePlan('team');
```

The widgets hand checkout and portal URLs back to you (`onCheckout`, `onOpen`), so the packages don't depend on a URL launcher.

The billing methods on the core `ui-core` and `authsome_core` clients still work, and are marked deprecated in favour of these packages.

## Operator routes

Plans, coupons, invoices and the ID-based subscription routes (`/subscriptions/:subId/...`)
are for operators and need `billing:manage`. They're listed in the plugin's
[README](https://github.com/xraph/authsome/tree/main/plugins/subscription), along with the
config and settings tables.
