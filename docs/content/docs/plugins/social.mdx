title: Social Login Plugin
description: OAuth2 social authentication with Google, GitHub, Microsoft, Apple, and custom providers.
---

The `social` plugin adds OAuth2 social login to Authsome. Users can sign in with their existing accounts from Google, GitHub, Microsoft, Apple, or any custom OAuth2 provider. The plugin handles the full OAuth2 flow, account linking, and profile data mapping.

## Setup

```go
import (
    "github.com/xraph/authsome"
    "github.com/xraph/authsome/plugins/social"
)

eng, err := authsome.NewEngine(
    // plus WithChronicle and WithWarden, which every engine needs (see Getting Started)
    authsome.WithStore(store),
    authsome.WithPlugin(social.New(social.Config{
        Providers: []social.Provider{
            social.NewGoogleProvider(social.ProviderConfig{
                ClientID:     "your-client-id",
                ClientSecret: "your-client-secret",
                RedirectURL:  "https://example.com/v1/social/google/callback",
                Scopes:       []string{"openid", "email", "profile"},
            }),
            social.NewGitHubProvider(social.ProviderConfig{
                ClientID:     "your-client-id",
                ClientSecret: "your-client-secret",
                RedirectURL:  "https://example.com/v1/social/github/callback",
            }),
        },
        SessionTokenTTL:   1 * time.Hour,
        SessionRefreshTTL: 30 * 24 * time.Hour,
    })),
)
```

## Configuration

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `Providers` | `[]Provider` | `[]` | List of enabled OAuth providers |
| `Domain` | `string` | `""` | Public base URL. A provider without a `RedirectURL` gets `{Domain}/v1/social/{provider}/callback` |
| `SessionTokenTTL` | `time.Duration` | `1h` | Lifetime of sessions created via social sign-in |
| `SessionRefreshTTL` | `time.Duration` | `30d` | Lifetime of refresh tokens |
| `HTTPClient` | `*http.Client` | guarded client | Makes every call to a generic OpenID Connect issuer. The default refuses private, loopback and link-local addresses; set your own to reach an issuer inside your network |

## Implemented interfaces

| Interface | Purpose |
|-----------|---------|
| `Plugin` | Base plugin identity (`"social"`) |
| `OnInit` | Captures store, bridges, ceremony store, and session config resolver |
| `RouteProvider` | Registers `/v1/social/:provider` and callback endpoints |
| `MigrationProvider` | Contributes the `oauth_connections` table |
| `AuthMethodContributor` | Reports linked social accounts as auth methods |
| `AuthMethodUnlinker` | Supports unlinking a social account from a user |

## Supported providers

The package has 22 constructors, all taking `social.ProviderConfig` (`ClientID`, `ClientSecret`, `RedirectURL`, `Scopes`): Amazon, Apple, Bitbucket, Discord, Dropbox, Facebook, GitHub, GitLab, Google, Instagram, Line, LinkedIn, Microsoft, Patreon, Pinterest, Slack, Spotify, Strava, Twitch, Twitter, Yahoo and Zoom (`social.NewGoogleProvider`, `social.NewGitHubProvider` and so on).

### Any OpenID Connect provider

If the provider speaks OpenID Connect, you don't need a constructor for it. Give authsome the issuer URL and it reads the endpoints and signing keys from the issuer's discovery document. That covers Keycloak, Okta, Auth0, Zitadel, Authentik and another authsome deployment running the OAuth2 provider plugin, so one product can offer "Sign in with Muono" where Muono is a second authsome deployment.

Most of the time an app adds one itself, through the admin API:

```bash
curl -X PUT "https://auth.example.com/v1/admin/social/providers/muono?app_id=$APP_ID" \
  -H "Content-Type: application/json" \
  -b "authsome_session=$SESSION" \
  -d '{
    "type": "oidc",
    "issuer": "https://id.muono.example",
    "display_name": "Muono",
    "client_id": "your-client-id",
    "client_secret": "your-client-secret"
  }'
```

The path segment (`muono`) is the provider's ID: lowercase letters, digits and dashes, up to 32 characters, and not one of the built-in names. Sign-in then runs at `/v1/social/muono`, and the client config lists the provider with `display_name` as its button label. Register `{Domain}/v1/social/muono/callback` as the redirect URI at the issuer.

Saving runs discovery straight away, so a wrong issuer comes back as a 400 when you save it, before anyone goes looking for a missing button. The issuer has to be an absolute `https` URL with no query or fragment.

You can also wire one in code:

```go
muono, err := social.NewOIDCProvider(ctx, social.OIDCConfig{
    ProviderConfig: social.ProviderConfig{
        ClientID:     "your-client-id",
        ClientSecret: "your-client-secret",
    },
    Name:   "muono",
    Issuer: "https://id.muono.example",
})
```

What the plugin does with the response:

- It verifies the id_token's signature against the issuer's published keys, along with its issuer, audience and expiry, and checks its nonce against the one sent at the start. A token that fails any of those never reaches account matching.
- The profile comes from the id_token's `sub`, `email`, `email_verified`, `given_name`, `family_name`, `name` and `picture` claims. When the id_token leaves the email out, the userinfo endpoint fills it in, but only if userinfo answers for the same `sub`.
- `email_verified` is read as a boolean or as the string `"true"`, since some issuers send a string. Anything else counts as unverified, so an address the issuer never verified can't link to an existing account.
- `openid` is always requested. Without your own `Scopes` the request is `openid email profile`.
- Discovery is cached per issuer for an hour.

The issuer URL comes from whoever administers the app, so the default client won't connect to private, loopback, link-local or shared (`100.64.0.0/10`) addresses. It checks the address at connect time, after DNS, so a name that later resolves somewhere internal is still refused. If your identity provider lives inside your network, pass your own `HTTPClient` in `Config`. That client then handles discovery, key fetches, the token exchange and userinfo for every generic provider.

### Custom provider

Implement the `Provider` interface to add any OAuth2 provider:

```go
type Provider interface {
    Name() string
    OAuth2Config() *oauth2.Config
    FetchUser(ctx context.Context, token *oauth2.Token) (*ProviderUser, error)
}
```

## Browser binding

A login started from a browser (the start request carries fetch metadata or an `Origin` header) sets a `__Host-authsome_oauth_state` cookie holding a digest of the login's state, and the callback for that state is refused unless it arrives with the matching cookie. Native clients, which send neither header, set no cookie and stay bound by the state and PKCE verifier.

## OAuth2 callback flow



**Start OAuth flow**: The client calls the start endpoint to get the authorization URL.

`POST /v1/social/:provider`

**Response:**

```json
{"auth_url": "https://accounts.google.com/o/oauth2/v2/auth?..."}
```

The plugin generates a cryptographic state parameter for CSRF protection and stores it in the ceremony store with a 10-minute TTL.


**User authorizes**: The user is redirected to the provider's consent screen and grants access.


**Callback**: The provider redirects back with an authorization code.

`GET /v1/social/:provider/callback?code=...&state=...`

The plugin validates the state parameter, exchanges the code for an access token, fetches the user profile from the provider, and either links to an existing user or creates a new one.

**Response:**

```json
{
  "user": {"id": "ausr_01j9...", "email": "alice@example.com"},
  "session_token": "a3f8c9d4...",
  "refresh_token": "d72b1ef8...",
  "provider": "google",
  "is_new_user": false
}
```



## Account linking

When a user signs in with a social provider, the plugin follows this logic:

1. Check if an OAuth connection already exists for this provider + provider user ID
2. If yes, look up the linked Authsome user and update tokens
3. If no, try to find a user by email
4. If a user with that email exists, link the social account to it
5. If no user exists, create a new user and link the social account

## Unlinking social accounts

Users can unlink a social provider from their account:

```go
err := socialPlugin.UnlinkAuthMethod(ctx, userID, "google")
```

The `CanUnlink` method checks whether the provider is managed by this plugin. The engine aggregates unlink requests across all `AuthMethodUnlinker` plugins.

## Providers per app

Providers saved through the admin API with `?app_id` belong to that app. Start, callback, unlinking and the client config all read the app's list, and an app with its own list uses it in place of the global one. Providers wired in code are always available and win over a saved provider with the same name.

## API routes

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v1/social/:provider` | Start OAuth flow, returns authorization URL |
| `GET` | `/v1/social/:provider/callback` | OAuth callback, exchanges code for session |
| `GET` | `/v1/admin/social/providers/catalog` | Built-in providers, plus an `oidc` entry marked `generic` for any OpenID Connect issuer |
| `GET` | `/v1/admin/social/providers` | Saved providers, secrets masked. `?app_id` shows what that app resolves to |
| `PUT` | `/v1/admin/social/providers/:provider` | Save a provider globally, or for one app with `?app_id` |
| `DELETE` | `/v1/admin/social/providers/:provider` | Remove a saved provider |

## Observability

The plugin emits events for:

- `auth.social.signup`: New user created via social login
- `auth.social.signin`: Existing user signed in via social login
