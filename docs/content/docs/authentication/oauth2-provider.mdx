title: OAuth2 Provider
description: Run Authsome as an OAuth2 authorization server with Authorization Code, PKCE, and Client Credentials flows.
---

Authsome can act as a full OAuth2 authorization server, allowing third-party applications to authenticate users and obtain access tokens through standard OAuth2 flows. This is distinct from [Social Login](/docs/authentication/social-login) (where Authsome is an OAuth2 *client*): here, Authsome issues its own tokens on behalf of your users.

## Setup

```go
import (
    "github.com/xraph/authsome"
    "github.com/xraph/authsome/plugins/oauth2provider"
)

eng, err := authsome.NewEngine(
    // plus WithChronicle and WithWarden, which every engine needs (see Getting Started)
    authsome.WithStore(store),
    authsome.WithPlugin(password.New()),
    authsome.WithPlugin(oauth2provider.New(oauth2provider.Config{
        Issuer:         "https://auth.myapp.com",
        AuthCodeTTL:    10 * time.Minute, // the default
        AccessTokenTTL: time.Hour,        // the default
    })),
)
```

The plugin's `Config` also covers the device flow (`DeviceCodeTTL`, `DeviceCodeInterval`, `VerificationURI`), dynamic client registration (`DynamicRegistration`, `RegistrationAppID`, `DynamicRegistrationScopes`, `RegistrationRateLimit`), RFC 8707 `ProtectedResources` and a `ConsentGate`. Its endpoints live under `/v1/oauth` (`/authorize`, `/token`, `/revoke`, `/userinfo`, `/consent`, `/register`, `/jwks`, `/device/authorize`, `/device/complete`) plus `/.well-known/openid-configuration`.

## Client registration

OAuth2 clients must be registered before they can request tokens. Clients represent third-party applications or services that consume your authentication API.

### Create a client

`POST /v1/admin/oauth/clients`

```json
{
  "name": "My Mobile App",
  "public": true,
  "redirect_uris": ["myapp://callback", "https://myapp.com/callback"],
  "scopes": ["openid", "profile", "email"],
  "grant_types": ["authorization_code"],
  "app_id": "aapp_..."
}
```

The body also takes `resources` (RFC 8707), `dpop_mode` and `first_party`, which skips the consent page.

**Response:**

```json
{
  "client_id": "aoc2_01jb...",
  "client_secret": "sec_a3f8c9d4e5f2g7h1...",
  "name": "My Mobile App",
  "public": true,
  "redirect_uris": ["myapp://callback", "https://myapp.com/callback"],
  "scopes": ["openid", "profile", "email"],
  "grant_types": ["authorization_code"],
  "created_at": "2024-11-01T10:00:00Z"
}
```

> **Important:** The `client_secret` is only returned once at creation time. Store it securely. Public clients (mobile/SPA apps) should use PKCE instead of a client secret.

### Client types

| `public` | Description | Use case |
|----------|-------------|----------|
| `false` (confidential) | Can securely store a client secret | Server-side applications, backend services |
| `true` (public) | Can't store a secret, so it uses PKCE | Mobile apps, single-page applications, CLI tools |

### In Go

The plugin has no client-creation method; register clients through the admin route above, or through `POST /v1/oauth/register` when dynamic registration is on. The model is `oauth2provider.OAuth2Client`.

## Authorization Code flow with PKCE

The Authorization Code flow with PKCE (Proof Key for Code Exchange) is the recommended flow for all client types. It is required for public clients and strongly recommended for confidential clients.



**Generate PKCE challenge**: The client generates a random `code_verifier` and derives a `code_challenge` from it.

```go
// Client-side
import "crypto/sha256"
import "encoding/base64"

codeVerifier := generateRandomString(64)
hash := sha256.Sum256([]byte(codeVerifier))
codeChallenge := base64.RawURLEncoding.EncodeToString(hash[:])
```


**Authorization request**: Redirect the user to the authorization endpoint.

```
GET /v1/oauth/authorize?
  response_type=code&
  client_id=aoc2_01jb...&
  redirect_uri=https://myapp.com/callback&
  scope=openid+profile+email&
  state=random_state_value&
  code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&
  code_challenge_method=S256
```

If the user isn't signed in yet, authsome sends them to your login page, as long as you've set one (see [Send signed-out users to your login page](#send-signed-out-users-to-your-login-page)). Once they're in, a third-party client shows them a consent screen listing the requested scopes. On approval, the browser goes back to the client with an authorization code.

```
HTTP/1.1 302 Found
Location: https://myapp.com/callback?code=auth_01jb...&state=random_state_value
```


**Token exchange**: The client exchanges the authorization code for tokens.

`POST /v1/oauth/token`

```
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=auth_01jb...&
redirect_uri=https://myapp.com/callback&
client_id=aoc2_01jb...&
code_verifier=the_original_code_verifier_string
```

**Response:**

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "rt_d72b1ef8...",
  "scope": "openid profile email",
  "id_token": "eyJhbGciOiJSUzI1NiIs..."
}
```



## Client Credentials grant

The Client Credentials grant is used for machine-to-machine authentication where no user context is needed. Only confidential clients can use this grant type.

`POST /v1/oauth/token`

```
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&
client_id=aoc2_01jb...&
client_secret=sec_a3f8c9d4e5f2g7h1...&
scope=api:read api:write
```

**Response:**

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "api:read api:write"
}
```

No refresh token is issued for client credentials grants: the client simply requests a new token when the current one expires.

## Token introspection

Resource servers can verify tokens by calling the introspection endpoint. This is useful for opaque tokens or when the resource server does not have access to the signing keys.

`POST /v1/introspect`

```
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(client_id:client_secret)

token=eyJhbGciOiJSUzI1NiIs...
```

**Response (active token):**

```json
{
  "active": true,
  "sub": "ausr_01j9...",
  "client_id": "aoc2_01jb...",
  "scope": "openid profile email",
  "iat": 1730451600,
  "exp": 1730455200,
  "iss": "https://auth.myapp.com",
  "token_type": "Bearer"
}
```

Every active response also carries `principal_kind` (`user`, `agent`, `workload` or `service_account`), and `delegated: true` when the token acts for `user_id` without being that user's own sign-in. An agent token, or a session minted by token exchange, is delegated. Its `user_id` still names the user it acts for, so check `delegated` before you treat the caller as that user. Both fields reach you even when your caller can't manage the app.

**Response (expired or revoked token):**

```json
{
  "active": false
}
```

## Token revocation

Clients can revoke tokens when they are no longer needed (e.g., on user logout):

`POST /v1/oauth/revoke`

```
Content-Type: application/x-www-form-urlencoded

token=eyJhbGciOiJSUzI1NiIs...&
token_type_hint=access_token&
client_id=aoc2_01jb...&
client_secret=sec_a3f8c9d4e5f2g7h1...
```

The endpoint always returns `200 OK` regardless of whether the token was found, to prevent token enumeration.

## Sign in with your app (OpenID Connect)

Once a client asks for the `openid` scope, the token endpoint returns an `id_token` next to the access token, and any OIDC library can sign users in against your deployment with an issuer URL, a client ID and a client secret. Nothing else needs configuring on the relying-party side.

### Set the issuer first

`Issuer` has to be the public URL your deployment is reachable at. Libraries fetch `{issuer}/.well-known/openid-configuration` and refuse any id_token whose `iss` differs from it.

```go
oauth2provider.New(oauth2provider.Config{
    Issuer:     "https://auth.myapp.com",
    IDTokenTTL: time.Hour, // the default
})
```

Leave it empty and the plugin falls back to `https://localhost`, logs a warning at startup, and no OIDC client will verify what you issue.

### Signing keys

You have two options. With no extra config, authsome manages the key for you. It generates an RSA-2048 key (signing with RS256), seals it with the engine's token encryptor, and stores it. The engine therefore needs an encryption key; with neither that nor an operator key, `openid` requests fail with a 500 and no access token goes out.

Managed keys rotate on a schedule. A key older than `IDTokenKeyRotation` (90 days by default) is replaced, and the old one stays in the JWKS for `IDTokenKeyRetireGrace` (7 days by default) so tokens it already signed still verify. An id_token lives for `IDTokenTTL` (1 hour by default), so the grace period is far longer than anyone needs.

You can rotate an app's own key from the dashboard, but at most once an hour, and only when the app has its own issuer (see below). The deployment issuer's key is shared by every app, so the dashboard won't rotate it. It rotates on its schedule.

If you'd rather hold the key yourself, hand the plugin a PEM private key. It wins over any managed key.

```go
oauth2provider.New(oauth2provider.Config{
    Issuer:                "https://auth.myapp.com",
    IDTokenSigningKeyFile: "/etc/authsome/id-token-key.pem", // or IDTokenSigningKey: pemBytes
    IDTokenSigningKeyID:   "2026-11",                        // optional, defaults to the RFC 7638 thumbprint
    IDTokenPreviousKeys:   [][]byte{oldPublicKeyPEM},         // published, never used to sign
})
```

An operator key is either RSA of at least 2048 bits or EC P-256 (ES256). One that doesn't parse, or an RSA key that's too small, stops the boot. You rotate it yourself: move the old key into `IDTokenPreviousKeys` and keep it there until every token it signed has expired. A previous key's `kid` is always its thumbprint, so if the old key signed under a custom `IDTokenSigningKeyID`, its tokens stop verifying once the `kid` changes.

If your deployment signs only with an ES256 operator key, discovery advertises only ES256. OIDC Discovery expects RS256 support, and a relying party that only accepts RS256 will reject your tokens. Keep an RSA key unless you know every client accepts ES256.

The JWKS lives at `{issuer}/v1/oauth/jwks` and is advertised as `jwks_uri`. It's served with `Cache-Control: public, max-age=300`, and HMAC keys never appear in it. If the signing keys can't be read from the store, the JWKS still answers with the access token keys, marked `Cache-Control: no-store` so no cache holds on to the partial set.

### One issuer per app

By default every client sees the deployment issuer. To give one app its own, turn on the `oauth2.app_issuer` setting (namespace `oauth2provider`, app scope, off by default). That app's clients then get the issuer `{Issuer}/apps/{slug}` and a key of their own, and these routes start answering for it:

| Method | Path |
|--------|------|
| `GET` | `/apps/:slug/.well-known/openid-configuration` |
| `GET` | `/apps/:slug/.well-known/oauth-authorization-server` |
| `GET` | `/apps/:slug/v1/oauth/jwks` |

An unknown slug and an app that hasn't opted in get the same 404.

<Callout type="warn">
  Turning `oauth2.app_issuer` on or off, or renaming the app's slug while it's on, changes the issuer for every OAuth2 client of that app. Each of them rejects tokens until you point it at the new issuer, so do it before they're live or announce it first.
</Callout>

### Claims

The id_token always carries `iss`, `sub`, `aud`, `azp`, `iat`, `exp` and `at_hash`, plus `nonce` and `auth_time` on the code flow, `auth_time` alone on the device flow, and neither on a refresh. The scopes the client was granted add the rest, and `GET` or `POST /v1/oauth/userinfo` returns the same set.

| Scope | Claims |
|-------|--------|
| `profile` | `name`, `given_name`, `family_name`, `picture`, `preferred_username`, `updated_at` |
| `email` | `email`, `email_verified` |
| `phone` | `phone_number`, `phone_number_verified` |

Empty strings are left out. The two booleans never are: a user without a verified address gets `email_verified: false`, not a missing claim.

Only the code, refresh and device grants mint an id_token. Client credentials and token exchange never do, and a client that doesn't ask for `openid` gets exactly the response it got before.

### Auth.js

Authsome's discovery document is enough for a generic OIDC provider:

```ts
import NextAuth from "next-auth";

export const { handlers, auth } = NextAuth({
  providers: [
    {
      id: "authsome",
      name: "Authsome",
      type: "oidc",
      issuer: "https://auth.myapp.com",
      clientId: process.env.AUTHSOME_CLIENT_ID,
      clientSecret: process.env.AUTHSOME_CLIENT_SECRET,
    },
  ],
});
```

Register the callback URL Auth.js shows you (`/api/auth/callback/authsome` for this id) as a redirect URI on the client, and include `openid profile email` in its scopes.

### go-oidc

```go
provider, err := oidc.NewProvider(ctx, "https://auth.myapp.com")
if err != nil {
    return err
}

conf := oauth2.Config{
    ClientID:     clientID,
    ClientSecret: clientSecret,
    RedirectURL:  "https://app.example.com/callback",
    Endpoint:     provider.Endpoint(),
    Scopes:       []string{oidc.ScopeOpenID, "profile", "email"},
}
verifier := provider.Verifier(&oidc.Config{ClientID: clientID})

// In the callback handler:
tok, err := conf.Exchange(ctx, code)
if err != nil {
    return err
}
raw, _ := tok.Extra("id_token").(string)
idToken, err := verifier.Verify(ctx, raw)
if err != nil {
    return err
}
var claims struct {
    Email         string `json:"email"`
    EmailVerified bool   `json:"email_verified"`
    Nonce         string `json:"nonce"`
}
if err := idToken.Claims(&claims); err != nil {
    return err
}
// Compare claims.Nonce with the nonce you sent on the authorize request.
```

go-oidc accepts only RS256 unless you say otherwise. If your deployment signs with an EC P-256 operator key, set `SupportedSigningAlgs: []string{oidc.ES256}` in `oidc.Config` (or list both `oidc.RS256` and `oidc.ES256` if you might switch).

The `nonce` you send on `/v1/oauth/authorize` can be up to 512 bytes. It's optional on the code flow.

### Send signed-out users to your login page

A "Sign in with your app" button only works if a signed-out user ends up somewhere they can sign in. Set `LoginURL` and authsome sends them there from `/v1/oauth/authorize`, with the full authorize request attached so they come straight back once they're in:

```go
oauth2provider.New(oauth2provider.Config{
    Issuer:   "https://auth.myapp.com",
    LoginURL: "/sign-in", // or "https://login.myapp.com/sign-in"
})
```

The user lands on `/sign-in?redirect=/v1/oauth/authorize?client_id=...`. Your sign-in page signs them in and then sends the browser to whatever `redirect` says, and authsome picks the request up from there (consent if the client needs it, then the code).

The value is a relative path when the login page is on the issuer's origin, which is what most sign-in pages expect, since they refuse to redirect off-site. A login page on another origin gets an absolute URL on the issuer, since a bare path would resolve against the wrong host. If your page reads a different parameter, set `LoginReturnParam`, for example to `return_to`.

Each app can have its own page too. Set **Login page** (`oauth2.login_url`) in the app's OAuth2 settings, and it wins over `LoginURL` for that app's clients. Both take a path starting with `/` or an absolute http(s) URL, and anything else is refused when you save it.

Leave both empty and a signed-out `/authorize` answers 401, as it did before.

A client that sends `prompt=none` never sees a login page. It's asking for an answer without any UI, so it gets `error=login_required` at its redirect URI (with its `state`) and decides what to do from there.

### Ask for a fresh sign-in

Sometimes a client needs to know the user signed in recently, say before changing a payout account. You have two ways to ask:

- `prompt=login` sends the user to the login page even when they're already signed in.
- `max_age=300` accepts a sign-in up to 300 seconds old. An older one goes to the login page first. `max_age=0` always asks.

The id_token's `auth_time` tells you when the sign-in you got actually happened, so check it if the answer matters to you.

When authsome sends a signed-in user back to the login page for `prompt=login`, the return URL drops `login` from the prompt and adds `login_after`, the time the trip started. The request that comes back is answered only for a session created after that, so the user can't loop and an old session can't sneak through. Your login page needs to show the sign-in form even when a session exists. The authsome UI sign-in page already does.

These return errors at the client's redirect URI, with its `state`:

| Request | Error |
|---------|-------|
| `prompt=none`, user signed out or sign-in too old | `login_required` |
| `prompt=none`, consent still needed | `consent_required` |
| `prompt=login` or `max_age` with no login page configured | `login_required` |
| `prompt=none` together with any other value | `invalid_request` |
| `max_age` that isn't a non-negative integer | `invalid_request` |

### Sign users out

When a user signs out of a client, the client can end their session here as well. Register where you want them sent afterwards:

```bash
curl -X PATCH "https://auth.myapp.com/v1/admin/oauth/clients/$CLIENT_ID" \
  -H "Content-Type: application/json" \
  -d '{"post_logout_redirect_uris": ["https://reports.example.com/signed-out"]}'
```

Then send the browser to the `end_session_endpoint` from discovery:

```
GET https://auth.myapp.com/v1/oauth/logout
    ?id_token_hint=<the id_token you got at sign-in>
    &post_logout_redirect_uri=https://reports.example.com/signed-out
    &state=abc
```

If the hint is an id_token this server issued for the user who's signed in, their session ends and the browser goes to your URI with `state` attached. The hint may have expired; it still counts, since logout often happens long after sign-in. Its signature, issuer and audience still have to check out.

Without a hint, or with one for somebody else, the user sees a page asking whether to sign out. That stops a link on some other site from signing people out. Pass `client_id` in place of the hint if you don't have one, and the page names your client.

`post_logout_redirect_uri` has to match one of the client's registered URIs exactly, with the same rules as `redirect_uris`. Leave it out and the user lands on a plain "You're signed out" page. Dynamic registration takes `post_logout_redirect_uris` too, and `POST` with a form body works the same as `GET`.

This ends the session on this server. It doesn't revoke tokens the client already holds, so revoke those yourself if the client needs to.

### Calling it from a browser app

A single-page app on another origin can talk to the provider directly: discovery, both key sets, token, userinfo, revoke and dynamic registration all answer CORS requests, preflights included. You don't need a backend just to swap the code for a token.

Any origin is allowed by default, and credentials never are. None of those endpoints reads a cookie (token and revoke authenticate the client, userinfo takes a bearer token), so letting any site read them doesn't expose anyone's session. Authorize, consent and logout do use the session cookie, and they're page navigations, so they get no CORS headers at all.

To narrow it, list your origins:

```go
oauth2provider.New(oauth2provider.Config{
    Issuer:      "https://auth.myapp.com",
    CORSOrigins: []string{"https://reports.example.com", "http://localhost:5173"},
})
```

If something in front of authsome already handles CORS, set `DisableCORS: true`. A host-wide CORS middleware that allows credentials for your own frontend can sit alongside this: these endpoints drop `Access-Control-Allow-Credentials` on the way out.

### What this doesn't do yet

Front-channel and back-channel logout aren't there yet, and neither is a way to add custom claims.

## Scopes and consent

### Built-in scopes

| Scope | Description |
|-------|-------------|
| `openid` | Required for OIDC. Returns an id_token (see [Sign in with your app](#sign-in-with-your-app-openid-connect)) |
| `profile` | Access to user's name, username, and profile image |
| `email` | Access to user's email address and email verification status |
| `phone` | Access to user's phone number and phone verification status |
| `offline_access` | Request a refresh token for long-lived access |

### Custom scopes

A client may request the scopes listed in its own `scopes`. There's no global allowlist in the configuration; dynamically registered clients are limited to `DynamicRegistrationScopes`.

### Consent screen

When a third-party client requests authorization, the user is shown a consent screen listing the requested scopes. The consent decision is remembered per user-client pair. To force re-consent:

```
GET /v1/oauth/authorize?...&prompt=consent
```

## Resource indicators (RFC 8707)

By default a token names no resource server. Any service that trusts your issuer will accept any token you issue, which means a token minted for one service is accepted by another, and the second service can't tell that the user only ever consented to the first. That is the confused deputy problem. Resource indicators close it: the client says which resource it wants a token for, and the server binds that name into the token as `aud`.

None of this is on by default. A client that sends no `resource` keeps getting exactly the token it gets today.

### Register what a client may target

A client may only request resources it was registered for. Add them at creation:

```json
{
  "name": "My Mobile App",
  "redirect_uris": ["myapp://callback"],
  "scopes": ["openid", "profile", "email"],
  "resources": ["https://api.example.com", "https://files.example.com"]
}
```

An empty list means the client may target nothing, so any request naming a resource is refused. That's deliberate, and it's the state every client registered before this existed is in. Those clients keep working, because they send no `resource` at all. Give a client an allowlist before you expect it to use one.

Each entry must be an absolute URI without a fragment, per RFC 8707 section 2. The same rule is enforced at registration and at request time, so a value you can store is a value that will match.

### Request a resource

Pass `resource` at the authorization endpoint. It repeats:

```
GET /v1/oauth/authorize
  ?response_type=code
  &client_id=aoc2_01jb...
  &redirect_uri=https://myapp.com/callback
  &resource=https://api.example.com
```

The token you get back carries that value:

```json
{
  "sub": "ausr_01j9...",
  "aud": ["https://api.example.com"],
  "scope": "openid profile email",
  "exp": 1730455200
}
```

You can also pass `resource` at the token endpoint to narrow further. Authorize for two resources, redeem for one, and the token carries only the one you asked for. You can't widen. Naming a resource the authorization didn't grant is refused with `invalid_target`. Omitting it at the token endpoint inherits everything the code carried.

Both work the same way on the client credentials and device authorization grants.

### Refuse a token meant for somebody else

Issuing an audienced token does nothing on its own. Something has to check it.

Set `session.resource_identifier` on the app to the URI this deployment answers to, and the auth middleware starts refusing tokens audienced elsewhere:

| Token `aud` | Setting | Result |
|-------------|---------|--------|
| absent | anything | authenticates, an unaudienced token is unrestricted |
| `https://api.example.com` | `https://api.example.com` | authenticates |
| `https://api.example.com` | `https://files.example.com` | refused |
| `https://api.example.com`, `https://files.example.com` | `https://api.example.com` | authenticates, one match is enough |

Leave the setting empty and no check runs at all, which is why turning this on is something you choose rather than something that happens to you on upgrade.

The check covers opaque tokens and JWTs alike. A JWT carries its audience in the token, and an opaque token carries it on the session row, so both are compared the same way.

### Errors

A rejected resource comes back as `invalid_target`, the code RFC 8707 registers, with a description naming which rule tripped:

```json
{
  "error": "invalid_target",
  "error_description": "resource \"https://evil.example.com\" is not registered for this client"
}
```

You will see it for an unregistered resource, a relative URI, a URI carrying a fragment, and an attempt to widen at the token endpoint.

### Discovery

The discovery document advertises support:

```json
{
  "resource_indicators_supported": true
}
```

Worth knowing: that field name isn't registered anywhere. RFC 8707 defines the `resource` parameter and the `invalid_target` error and no discovery metadata at all, and the RFC 8414 IANA registry has no entry for it. It's the convention the MCP ecosystem settled on, and it's what clients look for in practice, so read it as a de facto signal and not a standard one.

### A behaviour change worth reading before you upgrade

A JWT that fails any of the middleware's identity guards now stops there. Previously it fell through to opaque session resolution and then to the strategy registry, so a request could still authenticate by another route. It can't any more.

This bites in one specific shape: a request carrying both a JWT bearer token that gets refused and a separate credential a strategy would have accepted used to authenticate on the second credential. It now returns 401.

The guards this covers are the audience check above, the publishable-key app match, the revoked-session lookup, and IP and device binding. The reason for the change is that JWT access tokens are also stored as session tokens, so the old fallthrough looked a just-refused JWT up as an opaque session and checked the wrong field, quietly undoing the refusal.

## JWKS endpoint

The JSON Web Key Set (JWKS) endpoint publishes the public keys used to verify JWT access tokens and ID tokens:

`GET /.well-known/jwks.json`

```json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "key-2024-01",
      "use": "sig",
      "alg": "RS256",
      "n": "0vx7agoebGc...",
      "e": "AQAB"
    }
  ]
}
```

Resource servers should cache the JWKS and refresh it periodically or when they encounter a token signed with an unknown `kid`.

## OpenID Connect discovery

Authsome publishes an OpenID Connect discovery document:

`GET /.well-known/openid-configuration`

```json
{
  "issuer": "https://auth.myapp.com",
  "authorization_endpoint": "https://auth.myapp.com/v1/oauth/authorize",
```

## Configuration reference

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `Enabled` | `bool` | `false` | Enable OAuth2 provider functionality |
| `Issuer` | `string` | `""` | Issuer identifier URL (must be HTTPS in production) |
| `AccessTokenTTL` | `string` | `"1h"` | Access token lifetime |
| `RefreshTokenTTL` | `string` | `"30d"` | Refresh token lifetime |
| `AuthorizationCodeTTL` | `string` | `"10m"` | Authorization code validity |
| `RequirePKCE` | `bool` | `true` | Require PKCE for all authorization code grants |

## API routes

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/oauth/authorize` | Authorization endpoint (redirects user) |
| `POST` | `/oauth/token` | Token endpoint (code exchange, client credentials, refresh) |
| `POST` | `/introspect` | Token introspection |
| `POST` | `/oauth/revoke` | Token revocation |
| `GET`, `POST` | `/oauth/logout` | RP-initiated logout (`end_session_endpoint`) |
| `POST` | `/oauth/logout/confirm` | Answer to the logout confirmation page |
| `POST` | `/admin/oauth/clients` | Register a new OAuth2 client |
| `GET` | `/admin/oauth/clients` | List registered clients |
| `GET` | `/admin/oauth/clients/:clientId` | Get client details |
| `PATCH` | `/admin/oauth/clients/:clientId` | Update a client |
| `DELETE` | `/admin/oauth/clients/:clientId` | Delete a client |
| `GET` | `/.well-known/jwks.json` | JWKS endpoint |
| `GET` | `/.well-known/openid-configuration` | OIDC discovery document |
