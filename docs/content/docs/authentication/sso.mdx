title: Enterprise SSO
description: OIDC and SAML-based enterprise single sign-on with JIT user provisioning.
---

The `sso` plugin lets enterprise customers sign in through their company's identity provider (IdP) with OpenID Connect (OIDC) or SAML 2.0. Providers come from two places: the static list you pass in `sso.Config.Providers`, and connections created at runtime and stored per app, optionally scoped to one organization.

## Setup

```go
import (
    "github.com/xraph/authsome"
    "github.com/xraph/authsome/plugins/sso"
)

ssoPlugin := sso.New(sso.Config{
    // Static providers. Optional when you create connections at runtime.
    Providers: []sso.Provider{
        sso.NewOIDCProvider(sso.OIDCConfig{
            Name:         "okta",
            Issuer:       "https://acme.okta.com",
            ClientID:     "0oa1abcdef123456",
            ClientSecret: os.Getenv("OKTA_CLIENT_SECRET"),
            RedirectURL:  "https://myapp.com/v1/sso/okta/callback",
            Scopes:       []string{"openid", "email", "profile"},
        }),
    },
    // Public base URL, used for callback and ACS URLs.
    PublicBaseURL: "https://myapp.com",
    // Frontend origins a login may return to.
    AllowedReturnOrigins: []string{"https://app.myapp.com"},
})

eng, err := authsome.NewEngine(
    // plus WithChronicle and WithWarden, which every engine needs (see Getting Started)
    authsome.WithStore(store),
    authsome.WithPlugin(ssoPlugin),
)
```

`sso.Config` also has `SessionTokenTTL` and `SessionRefreshTTL`. [The SSO plugin page](/docs/plugins/sso) covers `NewOIDCProvider` and `NewSAMLProvider` in detail.

## Creating connections at runtime

A connection is one customer's IdP, matched by email domain:

```go
conn, err := ssoPlugin.CreateConnection(ctx, sso.CreateConnectionInput{
    AppID:        appID,
    OrgID:        orgID, // zero value means app-wide
    Provider:     "acme-okta",
    Protocol:     "oidc", // or "saml"
    Domain:       "acme.com",
    Issuer:       "https://acme.okta.com",
    ClientID:     "0oa1abcdef123456",
    ClientSecret: oktaSecret,
    Enforced:     true, // block password sign-in for acme.com (org owners and admins excepted)
})
```

For SAML, set `Protocol: "saml"` and `MetadataURL` (or `IDPMetadataXML`, or `IDPSSOURL` with `IDPCertificate`), plus `EntityID`, `ACSURL`, `SignRequests` and `AttributeMappings` as needed.

The stored connections are managed through `ssoPlugin.SSOStore()`, which has `GetConnection`, `GetConnectionByDomain`, `GetConnectionByProvider`, `ListConnections`, `UpdateConnection` and `DeleteConnection`. Set `Active` to false to switch one off without deleting it. Admins can also manage them over HTTP (below).

## Enterprise SSO flow



**Identify the connection**: The user enters their email and the engine looks up the SSO connection by email domain.

`POST /v1/sso/login`

```json
{"email": "alice@acme.com", "return_url": "https://app.myapp.com/after-login"}
```

`connection_id` pins one connection when the same domain belongs to several organizations. The response carries the IdP URL to send the browser to:

```json
{"login_url": "https://acme.okta.com/oauth2/v1/authorize?...", "state": "..."}
```

If you already know the provider, `POST /v1/sso/{provider}/login` starts the same flow by name.


**Redirect to IdP**: The engine generates the authorization URL (OIDC) or a SAML AuthnRequest (SAML) and redirects the user.


**IdP callback**: The user authenticates at the IdP and is redirected back to the Authsome callback URL.

For OIDC: `GET /v1/sso/{provider}/callback?code=...&state=...`
For SAML: `POST /v1/sso/{provider}/acs` (with `SAMLResponse` body)


**First sign-in**: If no user is linked to the IdP subject yet, the plugin links the existing account with that email (only if its email is verified; an unverified one is refused) or creates one, as long as the email's domain is the connection's `Domain` or in its `AllowedDomains`.


**Session created**: A full user + session is returned to the client.



## Provisioning on first sign-in

There's no switch for just-in-time provisioning: an SSO sign-in for an unknown address in an allowed domain creates the user. Restrict who can get in through the connection's `Domain` and `AllowedDomains`. With `TrustedFederation` on a connection, a user created through it takes the IdP's subject as the local user ID; it's off by default.

## API routes

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v1/sso/login` | Start a login from an email address |
| `POST` | `/v1/sso/{provider}/login` | Start a login with a named provider |
| `GET`, `POST` | `/v1/sso/{provider}/callback` | OIDC callback |
| `POST` | `/v1/sso/{provider}/acs` | SAML Assertion Consumer Service |
| `GET` | `/v1/sso/{provider}/metadata` | SAML SP metadata XML |
| `POST` | `/v1/sso/exchange` | Exchange the post-login code for a session |
| `POST` | `/v1/admin/sso/connections` | Create a connection (admin) |
| `GET` | `/v1/admin/sso/connections` | List connections (admin) |
| `GET` | `/v1/admin/sso/connections/{id}` | Get a connection (admin) |
| `PUT` | `/v1/admin/sso/connections/{id}` | Update a connection (admin) |
| `DELETE` | `/v1/admin/sso/connections/{id}` | Delete a connection (admin) |

The admin routes act only on the caller's own app. `app_id` in the create body and the list query is optional and must name that app; any other value is refused. A connection that belongs to another app is answered as not found.
