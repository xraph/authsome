---
title: Magic Links
description: Passwordless email sign-in with time-limited magic link tokens.
---

The `magiclink` plugin signs users in with a one-time link sent to their email address. They click the link and get a session; no password involved.

Magic links are ideal for:
- Applications where users sign in infrequently (reducing password friction)
- B2B tools where users may not remember a password set months ago
- Supplementing password auth as an alternative sign-in method

## Setup

```go
import (
    "context"

    "github.com/xraph/authsome"
    "github.com/xraph/authsome/plugins/magiclink"
)

eng, err := authsome.NewEngine(
    // plus WithStore, WithChronicle and WithWarden (see Getting Started)
    authsome.WithPlugin(magiclink.New(magiclink.Config{
        Mailer: magiclink.MailerFunc(func(ctx context.Context, email, token string) error {
            link := "https://myapp.com/auth/magic?token=" + token
            return sendLoginEmail(ctx, email, link) // your email code
        }),
    })),
)
```

<Callout type="warn">
The plugin sends only through `Config.Mailer`. It doesn't fall back to the engine's mailer bridge (`WithMailer`). Without a `Mailer`, `/send` still creates the token and answers success, but no email goes out.
</Callout>

`magiclink.Mailer` is one method, `SendMagicLink(ctx, email, token string) error`, and `MailerFunc` adapts a plain function. You build the link, so its URL and the email's wording are yours.

## How it works

1. The user submits their email address:

   `POST /v1/magic-link/send`

   ```json
   {"email": "alice@example.com", "app_id": "aapp_..."}
   ```

   If the address belongs to an account, the plugin creates a single-use token with the configured TTL and hands it to your `Mailer`. The response is `{"status": "magic link sent"}` either way, so the endpoint doesn't reveal which addresses exist. It doesn't create accounts for unknown addresses.

2. The user opens the link, and your frontend sends the token:

   `POST /v1/magic-link/verify`

   ```json
   {"token": "...", "app_id": "aapp_..."}
   ```

   A valid, unexpired, unused token returns a session:

   ```json
   {
     "user": {"id": "ausr_01j9...", "email": "alice@example.com"},
     "session_token": "a3f8c9d4...",
     "refresh_token": "d72b1ef8...",
     "expires_at": "2026-10-14T18:29:39Z"
   }
   ```

   The token is consumed, so a second request with it fails with 401.

## Configuration

```go
type Config struct {
    Mailer            Mailer        // sends the token; nothing is sent without it
    TokenTTL          time.Duration // default 10 minutes
    SessionTokenTTL   time.Duration // default 1 hour
    SessionRefreshTTL time.Duration // default 30 days
}
```

<Callout type="warn">
In a running engine the three durations come from the settings `magiclink.token_ttl_seconds` (600), `magiclink.session_token_ttl_seconds` (3600) and `magiclink.session_refresh_ttl_seconds` (2592000). Those settings have registered defaults, so the `Config` values are only used when no settings manager is available, which never happens inside an engine. To change a TTL, change the setting (globally or per app) through the settings API or the dashboard.
</Callout>

## Security considerations

- Tokens are single-use and expire after the TTL.
- `/verify` only accepts magic-link tokens, not other verification codes from the same table.
- `/send` is rate limited like resend-verification (`RateLimitConfig.ResendVerificationLimit`) plus a per-address limit, and `/verify` like email verification (`VerifyEmailLimit`).

## API routes

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v1/magic-link/send` | Create a token and pass it to the `Mailer` |
| `POST` | `/v1/magic-link/verify` | Exchange the token for a session |
