---
title: Vault Bridge
description: Secret management and feature flag integration via the Vault extension.
---

The Vault bridge gives your code access to Vault's secrets, feature flags and config through `eng.Vault()`. Authsome itself doesn't read anything through it today: no core code or plugin calls the bridge, so it's a convenience for your own startup code and plugins. Use it to fetch OAuth client secrets or SMTP credentials from Vault instead of the environment.

## Interface

The `bridge.Vault` interface is defined in `github.com/xraph/authsome/bridge`:

```go
type Vault interface {
    GetSecret(ctx context.Context, key string) ([]byte, error)
    SetSecret(ctx context.Context, key string, value []byte) error
    IsFeatureEnabled(ctx context.Context, flag string) bool
    GetConfig(ctx context.Context, key string) (string, error)
}
```

## Setup with the Vault adapter

The adapter wraps Vault's secret, flag and config services. Any of them can be nil; a nil service makes its methods return `bridge.ErrVaultNotAvailable`.

```go
import (
    "github.com/xraph/authsome"
    "github.com/xraph/authsome/bridge/vaultadapter"
)

// secretSvc, flagSvc and configSvc come from your Vault setup
// (*secret.Service, *flag.Service and *config.Service in github.com/xraph/vault).
vaultBridge := vaultadapter.New(secretSvc, flagSvc, configSvc,
    vaultadapter.WithAppID("myapp"),
)

eng, err := authsome.NewEngine(
    // plus WithChronicle and WithWarden, which every engine needs (see Getting Started)
    authsome.WithStore(pgStore),
    authsome.WithVault(vaultBridge),
)
```

## Use cases

### Storing OAuth client secrets

Instead of passing OAuth client secrets directly in the plugin constructor, retrieve them from Vault at startup:

```go
githubClientID, err := vaultBridge.GetSecret(ctx, "oauth.github.client_id")
if err != nil {
    log.Fatal(err)
}
githubClientSecret, err := vaultBridge.GetSecret(ctx, "oauth.github.client_secret")
if err != nil {
    log.Fatal(err)
}

eng, err := authsome.NewEngine(
    // plus WithChronicle and WithWarden, which every engine needs (see Getting Started)
    authsome.WithStore(pgStore),
    authsome.WithVault(vaultBridge),
    authsome.WithPlugin(social.New(social.Config{
        Providers: []social.Provider{
            social.NewGitHubProvider(social.ProviderConfig{
                ClientID:     string(githubClientID),
                ClientSecret: string(githubClientSecret),
                RedirectURL:  "https://myapp.com/v1/social/github/callback",
            }),
        },
    })),
)
```

### Feature flags on auth flows

Your own handlers and plugins can check Vault flags through the engine:

```go
// In your auth plugin or middleware, check a Vault feature flag:
if eng.Vault().IsFeatureEnabled(ctx, "passkey_registration_enabled") {
    // Allow passkey registration
}
```

### Dynamic configuration

Read config values the same way. Authsome won't pick them up on its own, so apply them yourself:

```go
sessionTTLStr, err := vaultBridge.GetConfig(ctx, "auth.session_ttl")
if err == nil {
    sessionTTL, _ = time.ParseDuration(sessionTTLStr)
}
```

## Standalone development stub

During development, use the built-in `NoopVault` stub:

```go
import "github.com/xraph/authsome/bridge"

eng, err := authsome.NewEngine(
    // plus WithChronicle and WithWarden, which every engine needs (see Getting Started)
    authsome.WithStore(memory.New()),
    authsome.WithVault(bridge.NewNoopVault()),
)
```

<Callout type="warn">
`NoopVault` returns `ErrVaultNotAvailable` for secret and config calls and `false` for every flag. If your startup code reads secrets through the bridge, it fails with the stub.
</Callout>
