The PostgreSQL store (`store/postgres`) is the backend to run in production. It sits on a Grove database opened with `pgdriver`, and `eng.Start(ctx)` creates its tables through Grove migrations.

## Installation

```bash
go get github.com/xraph/authsome
go get github.com/xraph/grove
go get github.com/xraph/grove/drivers/pgdriver
```

## Creating a store

```go
import (
    "log"
    "os"
    "time"

    "github.com/xraph/grove"
    "github.com/xraph/grove/driver"
    "github.com/xraph/grove/drivers/pgdriver"

    "github.com/xraph/authsome/store/postgres"
)

pg := pgdriver.New()
if err := pg.Open(ctx, os.Getenv("DATABASE_URL"),
    driver.WithPoolSize(25),
    driver.WithMaxConnLifetime(5*time.Minute),
); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(pg)
if err != nil {
    log.Fatal(err)
}

pgStore := postgres.New(db)
```

`postgres.New` takes a `*grove.DB` opened on the PostgreSQL driver and returns a `*postgres.Store` that implements `store.Store`. The pool options (`WithPoolSize`, `WithMinConns`, `WithMaxConnLifetime`, `WithMaxConnIdleTime`, `WithQueryTimeout`) come from `github.com/xraph/grove/driver`.

### Connection string format

```
postgres://user:password@host:5432/dbname?sslmode=disable
postgres://user:password@host:5432/dbname?sslmode=require&sslrootcert=/path/to/ca.pem
```

### Accessing the underlying DB

```go
rawDB := pgStore.DB() // the *grove.DB you passed in
```

## Wiring into the engine

```go
eng, err := authsome.NewEngine(
    authsome.WithStore(pgStore),
    authsome.WithDriverName("pg"),
    authsome.WithDB(db),
    authsome.WithChronicle(chronicleBridge),
    authsome.WithWarden(wardenEngine),
    authsome.WithPlugin(password.New()),
)
if err != nil {
    log.Fatal(err)
}

// Start runs the core and plugin migrations.
if err := eng.Start(ctx); err != nil {
    log.Fatal(err)
}
defer eng.Stop(ctx)
```

`WithDriverName("pg")` tells plugins which migration groups to contribute, and `WithDB(db)` gives plugins with their own stores (mfa, social, sso, oauth2provider, scim and others) the database; without it they keep their data in memory. Without the driver name, the core tables are created but the plugin-only ones (SSO identities, consents, the OAuth2 provider's tables and so on) aren't. The [Getting Started](/docs/getting-started) page shows how to build the Chronicle and Warden values and serve the API; the [Full Example](/docs/guides/full-example) runs the whole thing on PostgreSQL.

## Migrations

Unless you pass `WithDisableMigrate()`, `eng.Start(ctx)` applies the pending migrations: the store's core group plus every group the registered plugins return for the driver name. Grove records applied migrations in `grove_migrations`, so running `Start` on every boot is safe.

### Running migrations separately

To migrate in a deploy step rather than at server start, build an engine with the same store, driver name and plugins, and call:

```go
if err := eng.EnsureMigrated(ctx); err != nil {
    log.Fatal(err)
}
```

Then start the servers with `WithDisableMigrate()`. `EnsureMigrated` does nothing on an engine built with `WithDisableMigrate()`.

You can also call the store directly with extra groups: `pgStore.Migrate(ctx, groups...)`. A plugin that ships migrations implements `plugin.MigrationProvider`, whose `MigrationGroups("pg")` returns them.

## Table naming

All Authsome tables use the `authsome_` prefix to avoid collisions with application tables in a shared database:

| Table | Purpose |
|-------|---------|
| `authsome_apps` | Applications |
| `authsome_environments` | Environments per app |
| `authsome_users`, `authsome_user_emails` | Users and their addresses |
| `authsome_sessions`, `authsome_revoked_refresh_tokens` | Sessions and refresh-token replay records |
| `authsome_verifications`, `authsome_password_resets` | Email verification and reset tokens |
| `authsome_organizations`, `authsome_members`, `authsome_invitations`, `authsome_teams` | Organizations |
| `authsome_devices` | Devices |
| `authsome_webhooks`, `authsome_notifications` | Webhooks and notifications |
| `authsome_api_keys`, `authsome_service_accounts` | API keys and service accounts |
| `authsome_mfa_enrollments`, `authsome_mfa_recovery_codes` | MFA |
| `authsome_passkey_credentials` | Passkeys |
| `authsome_oauth_connections` | Linked social accounts |
| `authsome_sso_connections` | SSO connections |
| `authsome_delegations` | Delegations |
| `authsome_form_configs`, `authsome_branding_configs` | Dynamic forms and branding |
| `authsome_app_session_configs`, `authsome_app_client_configs` | Per-app session and client settings |
| `authsome_settings`, `authsome_kv` | Settings and key-value data |

Plugins add their own tables through their migration groups, for example `authsome_sso_identities` (sso), `authsome_consents` (consent), `authsome_scim_*` (scim), `authsome_waitlist_entries` (waitlist) and the `authsome_oauth*` tables of the OAuth2 provider.

## Lifecycle methods

| Method | Behaviour |
|--------|-----------|
| `Migrate(ctx, extraGroups...)` | Runs the core group and any extra groups through Grove's orchestrator. Idempotent |
| `Ping(ctx)` | Checks connectivity with `db.Ping` |
| `Close()` | Closes the `*grove.DB` |

## When to use

Use it for production and staging, and whenever more than one instance shares the user base: every instance reads the same tables, so you don't need sticky sessions.

## Machine API keys and schema compatibility

Use `Engine.CreateServiceAccountInEnvironment(ctx, appID, envID, name, description,
scopes)` to create a machine-key account. It checks that the environment exists and
belongs to the app before persisting the account. Then call
`Engine.CreateServiceAccountAPIKey` with the returned account ID. This is the
supported Engine bootstrap sequence; you do not need to write the store directly.

The admin HTTP create route and `Engine.CreateServiceAccount` still create app-wide
accounts. The admin API cannot assign an account environment yet.

`CreateServiceAccountAPIKey` copies the account's app and
environment and checks the requested scopes against its scopes. An app-wide account
is still valid, but key issuance returns `ErrServiceAccountEnvironmentRequired`
when its environment is empty. Choose the intended environment explicitly when
you create an account for API-key use. `MintChildPrincipal` rejects an unbound parent
before creating a child, and HTTP child minting returns 400 for this condition.

Machine keys require migration `20261009000001` and an Authsome artifact containing
`api_key_machine_owners`. Apply the migration before starting that artifact. The
migration preserves human keys and adds nullable `user_id` and `service_account_id`
ownership with exactly one owner. Foreign keys bind human owners to the key's app,
machine owners to its app and environment, and the key environment to its app.
Malformed existing rows stop the upgrade without changing or deleting credentials.

Deleting a service account cascades to its machine keys. Deleting an app removes its
keys and accounts; human user deletion retains the existing soft-delete behavior.
Updating an account's app or environment fails while keys still reference that
binding. Retire those keys deliberately before moving the account.

Rollback refuses while any machine key remains, including expired or revoked keys.
You can downgrade a human-only database without losing its keys. The check and schema
reversal share an exclusive table lock in one database statement, so concurrent
issuance cannot slip a machine row past the check.

An older reader sees a machine key's `user_id` as SQL NULL. It either fails the read
or rejects the missing human binding. It cannot authenticate that key as a human,
but it also cannot serve machine keys. Deploy compatible readers before enabling
machine-key traffic; no global capability floor is required for this migration.
