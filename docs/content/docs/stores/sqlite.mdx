---
title: SQLite
description: Lightweight embedded SQLite backend using Grove ORM with sqlitedriver.
---

The SQLite store (`store/sqlite`) provides an embedded, file-based backend using Grove ORM with `sqlitedriver`. It implements `store.Store` and needs no database server: everything lives in one file on disk.

## Installation

```bash
go get github.com/xraph/authsome
go get github.com/xraph/grove
go get github.com/xraph/grove/drivers/sqlitedriver
```

`sqlitedriver` wraps the pure-Go `modernc.org/sqlite`, so you don't need CGO or a system library.

## Creating a store

```go
import (
    "log"

    "github.com/xraph/grove"
    "github.com/xraph/grove/drivers/sqlitedriver"

    "github.com/xraph/authsome/store/sqlite"
)

lite := sqlitedriver.New()
if err := lite.Open(ctx, "file:authsome.db"); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(lite)
if err != nil {
    log.Fatal(err)
}

sqStore := sqlite.New(db)
```

The DSN is passed to `modernc.org/sqlite`. A `:memory:` DSN gives you a throwaway database that still runs the real migrations, unlike `store/memory`.

## Wiring into the engine

```go
eng, err := authsome.NewEngine(
    authsome.WithStore(sqStore),
    authsome.WithDriverName("sqlite"),
    authsome.WithDB(db),
    authsome.WithChronicle(chronicleBridge),
    authsome.WithWarden(wardenEngine),
    authsome.WithPlugin(password.New()),
)
if err != nil {
    log.Fatal(err)
}
if err := eng.Start(ctx); err != nil {
    log.Fatal(err)
}
defer eng.Stop(ctx)
```

`WithDriverName("sqlite")` lets plugins add their SQLite migrations, and `WithDB(db)` lets plugins with their own stores use the database instead of memory. Serve the API the way [Getting Started](/docs/getting-started) does.

## Migrations

Migrations run on `eng.Start(ctx)` unless you pass `WithDisableMigrate()`, through the same Grove orchestrator as PostgreSQL. Applied migrations are recorded in `grove_migrations` inside the file.

To run the core migrations yourself:

```go
if err := sqStore.Migrate(ctx); err != nil {
    log.Fatal("migration failed:", err)
}
```

## Table naming

SQLite uses the same `authsome_` table names as PostgreSQL. The DDL is SQLite's own, kept in `store/sqlite`'s migration group.

## Lifecycle methods

| Method | Behaviour |
|--------|-----------|
| `Migrate(ctx, extraGroups...)` | Runs the core group and any extra groups through the Grove orchestrator |
| `Ping(ctx)` | Checks the database with `db.Ping` |
| `Close()` | Closes the `*grove.DB` |

Call `Close()` before the process exits.

## Limitations compared to PostgreSQL

| Feature | SQLite | PostgreSQL |
|---------|--------|------------|
| Concurrent writers | One writer at a time | Many |
| Network access | A local file, so one host | Over the network |
| Multi-instance deployments | Not supported | Supported |
| Replication | None built in | Streaming replication |

## When to use

Use SQLite for local development, desktop apps and CLI tools, single-server deployments with light traffic, and integration tests where you want real SQL without running PostgreSQL.

## When not to use

Don't use it when you run more than one instance (the file can't be shared across hosts), when writes are heavy (SQLite serialises them), or when you need replication.
