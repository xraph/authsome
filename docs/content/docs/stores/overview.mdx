Authsome keeps persistence behind one composite interface, `store.Store` in `github.com/xraph/authsome/store`. The PostgreSQL, SQLite, MongoDB and in-memory backends all implement it. You pick the backend when you build the engine, and the engine and its plugins go through that interface from then on.

## The composite store interface

`store.Store` embeds the domain stores plus three lifecycle methods. Abridged:

```go
package store

import (
    "context"

    "github.com/xraph/authsome/account"
    "github.com/xraph/authsome/apikey"
    "github.com/xraph/authsome/app"
    "github.com/xraph/authsome/appsessionconfig"
    "github.com/xraph/authsome/device"
    "github.com/xraph/authsome/environment"
    "github.com/xraph/authsome/formconfig"
    "github.com/xraph/authsome/notification"
    "github.com/xraph/authsome/organization"
    "github.com/xraph/authsome/session"
    "github.com/xraph/authsome/user"
    "github.com/xraph/authsome/webhook"

    "github.com/xraph/grove/migrate"
)

type Store interface {
    user.Store
    session.Store
    account.Store
    app.Store
    organization.Store
    device.Store
    webhook.Store
    notification.Store
    apikey.Store
    environment.Store
    formconfig.Store
    formconfig.BrandingStore
    appsessionconfig.Store
    appclientconfig.Store
    settings.Store
    serviceaccount.Store
    principal.Store
    KV
    LegacyTokenHasher
    Retention
    Paged

    Migrate(ctx context.Context, extraGroups ...*migrate.Group) error
    Ping(ctx context.Context) error
    Close() error
}
```

## Sub-store interfaces

Each sub-store covers one Authsome domain. The table below summarises what each one manages:

| Interface | Package | Domain |
|-----------|---------|--------|
| `user.Store` | `github.com/xraph/authsome/user` | User CRUD, lookup by email/phone/username |
| `session.Store` | `github.com/xraph/authsome/session` | Session lifecycle, token and refresh-token lookup |
| `account.Store` | `github.com/xraph/authsome/account` | Email verifications, password resets |
| `app.Store` | `github.com/xraph/authsome/app` | Multi-app management |
| `organization.Store` | `github.com/xraph/authsome/organization` | Orgs, members, invitations, teams |
| `device.Store` | `github.com/xraph/authsome/device` | Device fingerprint tracking |
| `webhook.Store` | `github.com/xraph/authsome/webhook` | Webhook endpoint CRUD |
| `notification.Store` | `github.com/xraph/authsome/notification` | Notification queuing and delivery status |
| `apikey.Store` | `github.com/xraph/authsome/apikey` | API key storage and prefix lookup |
| `environment.Store` | `github.com/xraph/authsome/environment` | Environment (prod/staging/dev) isolation |
| `formconfig.Store` | `github.com/xraph/authsome/formconfig` | Dynamic sign-up form configuration |
| `formconfig.BrandingStore` | `github.com/xraph/authsome/formconfig` | Per-org branding configuration |
| `appsessionconfig.Store` | `github.com/xraph/authsome/appsessionconfig` | Per-app session token configuration overrides |
| `appclientconfig.Store` | `github.com/xraph/authsome/appclientconfig` | Per-app client configuration |
| `settings.Store` | `github.com/xraph/authsome/settings` | Dynamic settings |
| `serviceaccount.Store`, `principal.Store` | `github.com/xraph/authsome/serviceaccount`, `.../principal` | Service accounts and principals |
| `KV`, `Retention`, `Paged`, `LegacyTokenHasher` | `github.com/xraph/authsome/store` | Key-value data, retention sweeps, paged listing, legacy token lookups |

## Lifecycle methods

Every backend implements three lifecycle methods:

| Method | Signature | Behaviour |
|--------|-----------|-----------|
| `Migrate` | `Migrate(ctx context.Context, extraGroups ...*migrate.Group) error` | Runs all schema migrations. Extra groups passed here are merged with the core migrations and executed in a single orchestrator run. Plugins supply their own migration groups via this mechanism. |
| `Ping` | `Ping(ctx context.Context) error` | Verifies database connectivity. Useful for health checks and readiness probes. |
| `Close` | `Close() error` | Releases all database connections and frees resources. |

When the engine starts it asks every plugin that implements `plugin.MigrationProvider` for its groups (`MigrationGroups(driverName)`, with the name you set through `WithDriverName`), and passes them to `Migrate` together with the core group.

## Migration system

Migrations are Grove `migrate.Group` values run by `migrate.Orchestrator`. Each backend has a core group (`postgres.Migrations`, for example). On `eng.Start(ctx)`, unless you passed `WithDisableMigrate()`:

1. The engine collects the plugins' groups for the configured driver name.
2. It calls `store.Migrate(ctx, pluginGroups...)`.
3. The orchestrator records applied migrations in `grove_migrations` and skips them on later runs, so calling `Start` on every boot is safe.

`eng.EnsureMigrated(ctx)` runs the same steps without starting the engine, for a separate migration step.

## Choosing a backend

| Backend | When to use |
|---------|-------------|
| PostgreSQL | Production. The default choice |
| SQLite | Single-process deployments, local development, CLI tools, embedded applications |
| MongoDB | Teams already running a MongoDB cluster |
| Memory | Unit tests, CI and demos. Nothing survives a restart |

## Wiring a store into the engine

```go
import (
    "log"
    "os"

    "github.com/xraph/grove"
    "github.com/xraph/grove/drivers/pgdriver"

    "github.com/xraph/authsome"
    "github.com/xraph/authsome/store/postgres"
)

pg := pgdriver.New()
if err := pg.Open(ctx, os.Getenv("DATABASE_URL")); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(pg)
if err != nil {
    log.Fatal(err)
}

eng, err := authsome.NewEngine(
    authsome.WithStore(postgres.New(db)),
    authsome.WithDriverName("pg"),
    authsome.WithDB(db),
    authsome.WithChronicle(chronicleBridge),
    authsome.WithWarden(wardenEngine),
    // ... plugins and other options
)
```

`NewEngine` returns an error when the store, Chronicle or Warden is missing.

## Compile-time interface checks

Every backend file declares compile-time assertions to ensure the concrete type satisfies `store.Store`. The PostgreSQL backend, for example, includes:

```go
var _ store.Store = (*Store)(nil)
```

If you implement a custom store and miss any method, the build fails immediately rather than panicking at runtime.
