title: IP and Network Controls
description: How the client address is established behind proxies, how sessions can be bound to it, and the plugins that refuse sign-ins by country, reputation or anonymiser.

Every control that reasons about where a request came from starts with one question: what is the client's address? Authsome answers it once, in `middleware.ClientIP`, and everything else (rate limits, lockout, session binding, the audit trail, the plugins on this page) uses that answer.

## Trusted proxies

A `X-Forwarded-For` or `X-Forwarded-Proto` header is only believed when the immediate peer is a proxy the operator named. Anyone else's header is ignored, so a direct client cannot pick its own address, mint fresh rate-limit buckets, or dodge lockout.

The built-in set is the private ranges: loopback, `10/8`, `172.16/12`, `192.168/16`, link-local and `fc00::/7`. That is right for a load balancer on the same network and wrong for one on a public address, or for a network shared with workloads you do not control. Name your proxies:

```
AUTHSOME_TRUSTED_PROXIES=203.0.113.10/32,2001:db8::/48
```

The extension logs a warning at start while the built-in set is in use. From Go, `middleware.SetTrustedProxies` replaces the set and `middleware.TrustedProxiesAreDefault` reports whether it was ever set.

`middleware.IsHTTPS` applies the same rule to the scheme: TLS on the socket, or a trusted proxy's `X-Forwarded-Proto`. The session cookie's `Secure` attribute and the CSRF check both read it, so a forged header cannot downgrade either.

## Binding sessions

Two per-app settings bind a session to where it was created:

| Setting | Default | Effect |
|---------|---------|--------|
| `session.bind_to_ip` | `false` | A refresh from a different client address than the one the session recorded is refused. |
| `session.bind_to_device` | `false` | A refresh with a different `User-Agent` is refused. |

Binding to the address is a strong control on a fixed network and a nuisance on a mobile one, where addresses change as the device roams. Prefer DPoP-bound tokens for clients that can hold a key; use address binding for admin surfaces reached from an office network.

The cookie session also carries a cross-site check (see the CSRF section of the cookies documentation): a cookie-authenticated write must come from the same site or an allowlisted origin.

## Refusing by place, reputation or anonymiser

Three plugins refuse a sign-in or sign-up before any credential is checked. Each runs on `OnBeforeSignIn`, `OnBeforeSignUp` and `OnBeforePrincipalAuth`, so machine callers are covered as well as people. Each records what it refused on the audit trail.

### Geofence

Needs the `geoip` plugin for country lookup.

```go
import "github.com/xraph/authsome/plugins/geofence"

geofence.New(geofence.Config{
    DefaultPolicy:    "allow",
    BlockedCountries: []string{"KP"},
    BlockMessage:     "sign-in is not available from your region",
})
```

With `DefaultPolicy: "deny"`, only `AllowedCountries` may sign in.

### IP reputation

```go
import "github.com/xraph/authsome/plugins/ipreputation"

ipreputation.New(ipreputation.Config{
    Provider:       provider, // implements CheckIP(ctx, ip) (*IPReputation, error)
    BlockThreshold: 80,
    WarnThreshold:  50,
    CacheTTL:       6 * time.Hour,
})
```

A score at or above `BlockThreshold` refuses; one at or above `WarnThreshold` is flagged on the trail. Results are cached per address for `CacheTTL`, in a table bounded by `MaxCachedIPs` (10,000 by default).

### VPN, proxy and Tor

```go
import "github.com/xraph/authsome/plugins/vpndetect"

vpndetect.New(vpndetect.Config{BlockVPN: true, BlockProxy: true, BlockTor: true})
```

## Travel and anomaly

The `impossibletravel` plugin flags (or, with `Action: "block"`, refuses) a sign-in whose distance from the last one could not have been covered in the time between them; the `anomaly` plugin scores a sign-in against the account's own history of countries and hours. Both keep bounded in-memory histories, `MaxTrackedPrincipals` entries each, and both record alerts on the trail.

## Lockout by network

Failed sign-ins are counted per app, identifier and client network (`/24` for IPv4, `/64` for IPv6), so an attacker who fails from one network locks that network out of the account while the owner elsewhere still signs in. See [Account Lockout](/docs/security/lockout).
