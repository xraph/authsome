---
title: Rate Limiting
description: Every sensitive route is budgeted per client address, sign-in attempts are budgeted per target identifier as well, the counters live in the shared store, and a limiter that cannot answer fails closed.
---

Authsome puts a budget on every route an attacker would hammer: sign-in, sign-up, refresh, password reset, MFA, passkeys, SSO, SCIM, OAuth2 and the rest. Sign-in style routes get a second budget keyed on the account being tried, so an attacker rotating addresses gains nothing. Rate limiting is on by default and its counters live in the store's `authsome_kv` table, so one budget holds across every replica sharing the database.

## Two budgets

Route limits key on the client address, resolved through the trusted-proxy rules (see [IP and Network Controls](/docs/security/ip-control)). When the budget is spent the route answers `429` with `Retry-After`, `X-RateLimit-Limit` and `X-RateLimit-Remaining`.

Identifier limits key on what is being tried: the email, username or phone number, hashed before it becomes a key so the shared store never holds an address. They apply to sign-in, password reset, verification and the other places an identifier is presented, and a spent budget answers `429` too. Lockout, described on its own page, is the slower control that follows repeated failures from one network.

A limiter that returns an error is a limiter that cannot count. By default the request is refused with `503` and `Retry-After: 5`, because an outage of the shared store must not turn into an unlimited window. `FailOpen` reverses that for deployments that prefer availability, and every fail-open is counted on the `control.degraded` metric.

## Configuration

```go
cfg := authsome.DefaultConfig()
cfg.RateLimit.SignInLimit = 5
cfg.RateLimit.WindowSeconds = 60
cfg.RateLimit.FailOpen = false

engine, err := authsome.NewEngine(authsome.WithConfig(cfg) /*, store, warden, chronicle */)
```

Through the Forge extension's YAML:

```yaml
authsome:
  rate_limit:
    enabled: true
    window_seconds: 60
    signin_limit: 5
    signup_limit: 3
    refresh_limit: 10
    forgot_password_limit: 3
    fail_open: false
```

| Field | Default | Route |
|-------|---------|-------|
| `SignInLimit` | 5 | `/v1/auth/signin` and the identifier budget behind it |
| `SignUpLimit` | 3 | `/v1/auth/signup` |
| `RefreshLimit` | 10 | `/v1/refresh` |
| `IntrospectLimit` | 20 | `/v1/introspect` |
| `ForgotPasswordLimit` | 3 | password reset requests |
| `ResetPasswordLimit` | 5 | password reset completion |
| `ChangePasswordLimit` | 5 | password change |
| `VerifyEmailLimit` | 10 | email verification |
| `ResendVerificationLimit` | 3 | resend verification |
| `MFAChallengeLimit` | 5 | MFA challenge and verify |
| `PasskeyLimit` | 10 | passkey ceremonies |
| `OAuthTokenLimit` | 30 | `/v1/oauth/token` |
| `OAuthAuthorizeLimit` | 30 | `/v1/oauth/authorize` |
| `SSOLimit` | 20 | SSO start and callback |
| `SCIMLimit` | 60 | SCIM provisioning |
| `SSFPushLimit` | 60 | Shared Signals push |
| `WaitlistJoinLimit` | 5 | waitlist join |
| `APIKeyFailureLimit` | 20 | failed API key presentations |
| `WindowSeconds` | 60 | The window every limit counts in |
| `FailOpen` | false | Let requests through when the limiter errors |

Every limit is requests per window per client address. Zero disables that one limit.

## Limiters

The engine wires `ratelimit.NewKVLimiter(store)` over the store's key-value table, which is what a multi-replica deployment needs. The others:

```go
import "github.com/xraph/authsome/ratelimit"

engine, err := authsome.NewEngine(
    authsome.WithRateLimiter(ratelimit.NewMemoryLimiter()),
    // ...
)
```

`NewMemoryLimiter` counts in the process and is bounded (`NewMemoryLimiterWithLimit` sets the bound); it suits one replica and tests. `NewNoopLimiter` allows everything and is for tests only. A custom limiter implements two methods:

```go
type Limiter interface {
    Allow(ctx context.Context, key string, limit int, window time.Duration) (bool, error)
    Remaining(ctx context.Context, key string, limit int, window time.Duration) (int, error)
}
```

## Limiting your own routes

Plugins and embedding code reuse the engine's limiter and window:

```go
g.POST("/v1/things", handler, forge.WithMiddleware(engine.RateLimitMiddleware(30)))
```

`middleware.RateLimit(limiter, cfg)` is the middleware itself; `middleware.RateLimitConfig` carries the limit, the window, an optional key function (the client address by default), `FailOpen`, and `OnError`, `OnReject` and `OnFailOpen` callbacks for metrics.

## Metrics and the trail

`ratelimit.rejected` counts route refusals, `identifier_limit.rejected` counts identifier refusals, `ratelimit.error` counts limiter errors and `control.degraded` counts the requests a fail-open let through. A refused sign-in is also on the audit trail with reason `rate_limited`.
