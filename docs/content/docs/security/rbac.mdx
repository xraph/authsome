---
title: Roles and Permissions
description: Roles carry permissions, users hold roles, and every check goes through Warden. What the built-in roles are, how to define your own, and how routes and code ask the question.
---

Authsome answers "may this caller do this to that" through [Warden](https://github.com/xraph/warden), the Forge authorization engine. Roles and their permissions are stored in Warden, a session carries the caller's role slugs, and both the HTTP routes and your own code ask the same function. Warden is required: the engine does not start without one.

## The model

```go
import "github.com/xraph/authsome/rbac"

type Role struct {
    ID          string
    AppID       string
    EnvID       string
    ParentID    string // empty for a root role
    Name        string
    Slug        string
    Description string
}

type Permission struct {
    ID       string
    RoleID   string
    Action   string // read, update, delete, manage, ...
    Resource string // user, session, app, organization, role, ...
}

type UserRole struct {
    UserID string
    RoleID string
    OrgID  string // empty means the whole app
}
```

A role belongs to one app. A permission is one action on one resource, granted to one role. A user holds roles either across the app or within one organization. A role may have a parent; a child inherits the parent's permissions.

Actions and resources are not free text. Warden holds a schema per resource that names its relations and which of them satisfy each action. The core schemas are:

| Resource | Actions |
|----------|---------|
| `user` | `read`, `update`, `delete`, `manage`, `ban`, `impersonate` |
| `session` | `read`, `create`, `delete`, `revoke` |
| `device` | `read`, `create`, `update`, `delete`, `trust` |
| `app` | `read`, `update`, `delete`, `manage`, `manage_roles`, `manage_envs` |
| `organization` | `read`, `update`, `delete`, `manage`, `manage_members` |
| `role` | `read`, `create`, `update`, `delete`, `assign`, `unassign` |
| `permission` | `read`, `create`, `delete` |
| `environment` | `read`, `create`, `update`, `delete` |

One consequence worth knowing: `read` on `user` is satisfied by the `app` relation, which every user of an app holds. It gates nothing. The entitlement every admin surface checks is `manage` on `app`.

## Built-in roles

Bootstrap creates three roles per app, with the slugs in the `rbac` package:

| Slug | Constant | Who |
|------|----------|-----|
| `owner` | `rbac.AppOwnerSlug` | The app's owner. Holds `manage` on `app` and everything under it. |
| `admin` | `rbac.AppAdminSlug` | Administrators. Holds `manage` on `app` but not `delete`. |
| `user` | `rbac.AppUserSlug` | Every signed-up user. Assigned on sign-up by `EnsureDefaultRole`. |

The platform app has its own three (`platform-user`, `platform-admin`, `platform-owner`, with `rbac.IsPlatformRole` to tell them apart). The first user to sign up on the platform app becomes its owner once their email is verified.

## Defining roles

```go
role := &rbac.Role{AppID: appID.String(), Name: "Support", Slug: "support"}
if err := engine.CreateRole(ctx, role); err != nil {
    return err
}
if err := engine.AddPermission(ctx, &rbac.Permission{RoleID: role.ID, Action: "read", Resource: "session"}); err != nil {
    return err
}
if err := engine.AddPermission(ctx, &rbac.Permission{RoleID: role.ID, Action: "revoke", Resource: "session"}); err != nil {
    return err
}
```

`GetRole`, `GetRoleBySlug`, `UpdateRole`, `DeleteRole`, `ListRoles`, `ListRolePermissions`, `RemovePermission` and `GetRoleChildren` complete the set. A role slug is unique within its app.

## Assigning roles

```go
err := engine.AssignUserRole(ctx, &rbac.UserRole{UserID: userID.String(), RoleID: role.ID})
```

Set `OrgID` to confine the assignment to one organization. `UnassignUserRole`, `ListUserRoles`, `ListUserRolesInApp`, `ListUsersWithRole` and `ListUserRoleSlugs` read and undo it. A session minted after the change carries the new slugs; a session already open carries the slugs it was minted with until it is refreshed.

## Ceilings

A caller cannot hand out more than they hold. Assigning a role, granting an organization role, or minting a session for a service account checks that the target is no wider than the caller's own; a request that would escalate is refused. The OAuth2 provider applies the same rule to scopes: a client cannot be granted scopes the consenting user does not hold.

## Checking permissions

In code:

```go
allowed, err := engine.HasPermission(ctx, userID, "manage", "app")
```

`HasPermission` is for a user. `Can` takes any principal (a user, a service account, an agent) and the actor chain behind it, and requires that every link in the chain is allowed, so a delegated caller can never do more than either party could alone:

```go
allowed, err := engine.Can(ctx, principal.UserRef(userID), nil, "revoke", "session")
```

On a route:

```go
g := router.Group("/v1", forge.WithGroupMiddleware(
    middleware.RequireAuth(),
    middleware.RequirePermission(engine, "manage", "app"),
))
```

`RequirePermission` answers `403` when the check fails and `401` when nobody is signed in. It is chain-aware: when the session carries an actor chain, each actor is checked too.

## Routes

Each route requires the matching action on `role` or `permission`, checked with `RequirePermission`:

| Method | Path | Requires | What it does |
|--------|------|----------|--------------|
| `POST` | `/v1/roles` | `create` on `role` | Create a role |
| `GET` | `/v1/roles` | `read` on `role` | List the app's roles |
| `GET` | `/v1/roles/:roleId` | `read` on `role` | One role |
| `PATCH` | `/v1/roles/:roleId` | `update` on `role` | Rename or re-parent it |
| `DELETE` | `/v1/roles/:roleId` | `delete` on `role` | Delete it |
| `POST` | `/v1/roles/:roleId/permissions` | `create` on `permission` | Grant an action on a resource |
| `GET` | `/v1/roles/:roleId/permissions` | `read` on `permission` | List the role's permissions |
| `DELETE` | `/v1/roles/:roleId/permissions/:permissionId` | `delete` on `permission` | Revoke one |
| `POST` | `/v1/roles/:roleId/assign` | `assign` on `role` | Give the role to a user |
| `POST` | `/v1/roles/:roleId/unassign` | `unassign` on `role` | Take it away |
| `GET` | `/v1/users/:userId/roles` | `read` on `role` | A user's roles |

Every create, update, delete, assign and unassign is on the audit trail with the role, the user and who did it.
